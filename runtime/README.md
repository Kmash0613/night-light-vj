# ランタイム（Three.js）

要件定義書 §5, §9 参照。

## Phase 1（実装済み・実機での確認待ち）

写真1枚で、MIDI Note On による輝度の明滅を確認する。カメラは固定（移動なし）。

**設計方針: 個別の光点（パーティクル）は打たない。** 写真から「輝度マップ」（重み画像）を作り、
MIDIノートに応じてそのマップの値が乗っている場所だけ、元の写真そのものの明るさを上げ下げする。
マップが0の場所（暗い背景など）は変化しない。

**クラスタ分けは今は無し。** 検出した領域はすべて同じ1チャンネルの重みマップに含まれ、
`config/midi-mapping.json` の `name: "KICK"` のトラックのNote Onに一律に連動する
（見つからない場合は `cluster_trigger` 全体をKICK扱いにフォールバックする）。
トラックごとに別々の場所を光らせるクラスタ分けは、動作が安定してから改めて検討する。

### 輝度マップの生成（要件定義書 §4 の簡易版・ブラウザ内実装）

写真を読み込むと自動で実行される（`extractLuminanceMask()` in `main.js`）。

1. 輝度（`0.2126R+0.7152G+0.0722B`）を計算し、上位 `top %` の明るいピクセルの閾値を求める
2. **画素ごとに直接**、閾値を超えた画素だけ「その画素自身の輝度 / 255」（最低0.35）を
   重みとして1チャンネルの重みマップ（RGBAキャンバスのRチャンネルのみ使用）に書き込む

以前は4連結の連結成分ラベリングで塊（領域）を作り、塊ごとに「閾値からの超過量」を重みに
していたが、この方式は**閾値の位置によって0除算的に重みが全て0になる**（白飛びが多い写真で
閾値が255に張り付くと、閾値を超える画素は必ずluma===255なので超過量が常に0になる）ことや、
**塊がたまたま画像の広い範囲を覆ってしまう**ことが繰り返し起きた。重みを画素自身の輝度で
決める今の方式は threshold の位置に関係なく数学的に0除算にならず、`targetCount <= 総画素数`
が保証される以上「該当画素が0個で輝度マップが空になる」ことも起こり得ない。

「Auto Extract」パネルの「再抽出」で `top %` を変えて再実行できる。
`mask-editor/` で作った `points.json` を読み込むと、各点を中心にソフトな円を同じ形式へ
スタンプしてマップを作る（自動抽出の代わりに手動データを使いたいとき用）。

**過去に踏んだ2つのバグ（修正済み）:**

1. 輝度マップを書き込む `canvas` のアルファチャンネルを0のまま（`createImageData` の初期値）
   にしていたため、ブラウザのcanvas内部実装（premultiplied alpha）が `putImageData`/
   `getImageData` の往復や `THREE.CanvasTexture` としてWebGLへアップロードする際に、
   アルファ0の画素のRGBを丸ごと0に潰していた。結果、重みマップは常に「重み0」しか
   持てず、KICKが来ても写真の明るさが一切変化しない状態になっていた
   （`extractLuminanceMask`/`pointsToMaskCanvas` とも、書き込む全画素のアルファを255に
   することで解消）。
2. 上位 `top %` の閾値をヒストグラム（丸めた輝度でバケット化）から求めているのに、実際に
   画素を採用するかどうかの判定は丸めていない生の輝度値と比較していたため、単色に近い
   塗りつぶし領域（建物のシルエットなど）の輝度が閾値のすぐ下の小数（例: 33.7）だと、
   丸めればヒストグラム上はカウントされるのに実際のフィルタでは弾かれ、指定した `top %`
   よりはるかに少ない画素しか検出されないことがあった（`luma[]` 自体を丸めた整数として
   保持することで解消）。

### 明滅（背景シェーダー内で完結）

背景メッシュは独自の `ShaderMaterial`（`map`=元の写真, `maskMap`=輝度マップ）。
フラグメントシェーダーで、写真の各画素の明るさに `factor = 1 + brightGain * weight * kickEnvelope`
を掛ける（`weight` はその画素のマップ値）。`factor` は1以上なので明るくなる方向にのみ振れる。

- KICKエンベロープ: `env = velocity/127 * exp(-t/tau)`。`name: "KICK"` にマッチする
  トラックが複数あれば最大値を採用する（CPU側で計算しシェーダーへuniform渡し）
- `bright gain` は明滅の強さ全体のゲイン

**ambient breathing（MIDIが無い間の自動揺らぎ、0を中心に上下する符号付きサイン波）は
検証を単純化するためいったんオミットしている。** 上記2つのバグでKICKトリガー自体が
機能しているかどうかの切り分けが難しかったため、まずKICKのNote Onだけで明滅することを
確認できるプリミティブな構成に戻した。安定して確認できたら再度追加する。

### ブルーム

selective bloomではなく通常の `UnrealBloomPass`（画面全体の輝度がthresholdを超えた画素が光る）。
KICKで明るくなった場所（またはもともと明るい場所）がしきい値を超えれば自然に光る。
「Bloom」パネルのスライダーで調整（SEQTRAKのFX LEVEL CCでも `strength` を操作可能）。

### 色まわり

- `renderer.toneMapping` は `NoToneMapping`。背景シェーダーは手動で sRGB→linear変換してから
  明るさを掛け、`OutputPass` が最後に linear→sRGB に戻す（二重トーンマッピングを避ける）

### その他

- Three.js は `index.html` の importmap で CDN (unpkg) から読み込む。ビルド不要
- `../config/midi-mapping.json` を起動時に `fetch` する。`file://` では動かないため、
  ローカルサーバー経由（`python -m http.server`）か GitHub Pages 経由で開くこと
- 写真・光点データは `<input type="file">` でローカル読み込みし、どこにも送信しない
