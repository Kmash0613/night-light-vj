# ランタイム（Three.js）

要件定義書 §5, §9 参照。

## Phase 1（実装済み・実機での確認待ち）

写真1枚で、MIDI Note On による輝度の明滅を確認する。

**設計方針: 個別の光点（パーティクル）は打たない。** 写真から「輝度マップ」（重み画像）を作り、
MIDIノートに応じてそのマップの値が乗っている場所だけ、元の写真そのものの明るさを上げ下げする。
マップが0の場所（暗い背景など）は変化しない。

**クラスタは最大4つ（0-3）。** 輝度マップはRGBAの4チャンネルテクスチャで、各チャンネルが
1クラスタの重みに対応する。`config/midi-mapping.json` の `cluster_trigger` トラックは
`cluster` フィールド（0-3）で自分の紐づく先を決め、Note Onが来るとそのクラスタの重みが
乗っている場所だけ明るさが上がる。一度、動作確認を単純化するためクラスタ分けを丸ごと無くし
KICK一本にしていたが、明滅の土台が安定して確認できたので復活させた
（cluster不明のエントリはcluster0にフォールバックする）。

### 出力フレーム（16:9固定・コンテインフィット）

レンダラー・カメラのフラスタムは常に16:9固定（`OUTPUT_ASPECT` in `main.js`）。
写真の縦横比がそれと違っても、写真自体は歪ませず（メッシュのスケールは常に等倍）、
"contain" fit（CSSの`background-size:contain`と同じ）で16:9フラスタム内に必ず全体が
収まるように縮小する。クロップは一切発生せず、横長の写真は上下に、縦長の写真は左右に
黒帯が出る。ブラウザのウィンドウ/パネル幅が16:9と違う形でも、レンダラーのサイズ自体を
その中に収まる最大の16:9矩形に決めるので（`resize()`）、その分も含めて余りは全部
`#viewport`の黒帯になる。

### 輝度マップの生成（要件定義書 §4 の簡易版・ブラウザ内実装）

写真を読み込むと自動で実行される（`extractLuminanceMask()` in `main.js`）。

1. 輝度（`0.2126R+0.7152G+0.0722B`）を計算し、上位 `top %` の明るいピクセルの閾値
   （黒点、=threshold）を求める
2. **画素ごとに直接**、閾値を超えた画素だけを重みとして書き込む。重みは
   「threshold（黒点）〜実際に写っている最大輝度（白点、=そのヒストグラムでの
   最大の非ゼロビン）」を毎回0-1に正規化してから0.35-1の範囲にマップする
   （`weight = 0.35 + 0.65 * clamp01((luma - threshold) / (whitePoint - threshold))`）。
   写真ごとに露出や白飛びの度合いが違っても（同じネオンでもあるコマは255まで飽和、
   別のコマは180止まり等）、そのコマの中で最も明るい画素は常にweight=1になる。
   スライドショーで複数の写真を切り替えたときの発光のムラ（写真間でのホワイト
   ポイント/ブラックポイントの差）を吸収するための処理。白飛びが無く閾値以上が
   全部同じ輝度の場合（dynamicRange=0）は正規化しようが無いので一律weight=1にする。
   書き込み先のチャンネル（＝クラスタ）は、閾値を超えた画素全体を
   `clusterQualifyingPixels()` のk-meansでまとめて分けて決める（要件定義書 §4
   「クラスタリング軸：深度を主、画面上のXY座標を従とする」）。深度は本物の推定モデルが
   無いため疑似深度（Y位置＋輝度。Phase 2の `generatePseudoDepthGrid()` と同じ式）で
   代用し、XY座標を従軸として弱く効かせる。手前寄りの群から順にcluster0,1,2...と振り直す
   （cluster0が最も手前＝config側のKICK=cluster0の慣習に合わせる）

以前は4連結の連結成分ラベリングで塊（領域）を作り、塊ごとに「閾値からの超過量」を重みに
していたが、この方式は**閾値の位置によって0除算的に重みが全て0になる**（白飛びが多い写真で
閾値が255に張り付くと、閾値を超える画素は必ずluma===255なので超過量が常に0になる）ことや、
**塊がたまたま画像の広い範囲を覆ってしまう**ことが繰り返し起きた。重みを画素自身の輝度で
決める今の方式は threshold の位置に関係なく数学的に0除算にならず、`targetCount <= 総画素数`
が保証される以上「該当画素が0個で輝度マップが空になる」ことも起こり得ない。クラスタの
割り当てはその後段の別処理（k-means）なので、この重み計算の安全性には影響しない。
より単純だった「画面のY位置だけで4等分する」割り当てを経て、今のk-means方式に発展させた
（Y位置だけだと、横に並ぶ別々の光点群が同じ高さというだけで1クラスタに混ざってしまうため）。

「Auto Extract」パネルの「再抽出」で `top %` を変えて再実行できる。
`mask-editor/` で作った `points.json` を読み込むと、各点を中心にソフトな円を同じ形式へ
スタンプしてマップを作る（自動抽出の代わりに手動データを使いたいとき用）。

**過去に踏んだバグ（修正済み）:**

1. 輝度マップを書き込む `canvas` のアルファチャンネルを0のまま（`createImageData` の初期値）
   にしていたため、ブラウザのcanvas内部実装（premultiplied alpha）が `putImageData`/
   `getImageData` の往復や `THREE.CanvasTexture` としてWebGLへアップロードする際に、
   アルファ0の画素のRGBを丸ごと0に潰していた。結果、重みマップは常に「重み0」しか
   持てず、KICKが来ても写真の明るさが一切変化しない状態になっていた
   （当時は全画素のアルファを255にする回避策で対処したが、下記3.で根本的に解消）。
2. 上位 `top %` の閾値をヒストグラム（丸めた輝度でバケット化）から求めているのに、実際に
   画素を採用するかどうかの判定は丸めていない生の輝度値と比較していたため、単色に近い
   塗りつぶし領域（建物のシルエットなど）の輝度が閾値のすぐ下の小数（例: 33.7）だと、
   丸めればヒストグラム上はカウントされるのに実際のフィルタでは弾かれ、指定した `top %`
   よりはるかに少ない画素しか検出されないことがあった（`luma[]` 自体を丸めた整数として
   保持することで解消）。
3. クラスタ復活でアルファチャンネル自体がcluster3の実データになったため、上記1.の回避策
   （アルファを255固定にする）が使えなくなった。根本原因は「2Dキャンバス経由でWebGL
   テクスチャを作ると、ブラウザ内部のpremultiplied alpha実装に引っかかりうる」ことなので、
   `<canvas>`/`CanvasTexture` を経由するのをやめ、生の `Uint8Array` から直接
   `THREE.DataTexture` を作る方式に変更した。`texImage2D` へ生バイト列がそのままアップ
   ロードされるだけで、canvasの内部表現も `putImageData`/`getImageData` の往復も一切発生
   しないため、4チャンネルとも安全にデータとして使える（`makeMaskTexture()` in `main.js`）。

### 明滅（背景シェーダー内で完結）

背景メッシュは独自の `ShaderMaterial`（`map`=元の写真, `maskMap`=RGBA4チャンネルの輝度マップ）。
フラグメントシェーダーで、写真の各画素の明るさに
`factor = 1 + brightGain * (totalWeight * baseLevel + dot(w, clusterEnvelope))` を掛ける
（`w` はその画素のマップ値=vec4、`totalWeight` はその合計をclampしたもの、
`clusterEnvelope` は4クラスタ分のエンベロープをまとめたvec4）。

- クラスタエンベロープ: `env_c = velocity/127 * exp(-t/tau)`。クラスタ `c` にマッチする
  トラックが複数あれば最大値を採用する（CPU側で計算しシェーダーへvec4のuniformで渡す）
- `bright gain` は明滅の強さ全体のゲイン
- `base level` は待機中（どのクラスタも鳴っていないとき）の定数ベースライン。0以下の
  スライダーで、マイナスにするとマップが乗っている場所は待機中は元の写真より暗く沈み、
  そのクラスタのノートが来たときだけそこから明るく持ち上がる。0なら待機中は写真のまま
  静止する（従来通り）。

**ambient breathing（MIDIが無い間の自動揺らぎ、0を中心に上下する符号付きサイン波）は
検証を単純化するためいったんオミットしている。** 過去に踏んだバグでトリガー自体が
機能しているかどうかの切り分けが難しかったため、まずクラスタのNote Onだけで明滅することを
確認できるプリミティブな構成に戻した。`base level` は定数オフセットのみで揺らぎは無い、
その簡易版にあたる。安定して確認できたら、ambient breathingの方は再度追加する。

### ブルーム

selective bloomではなく通常の `UnrealBloomPass`（画面全体の輝度がthresholdを超えた画素が光る）。
クラスタのノートで明るくなった場所（またはもともと明るい場所）がしきい値を超えれば自然に光る。
「Bloom」パネルのスライダーで調整（SEQTRAKのFX LEVEL CCでも `strength` を操作可能）。

### Post FX（モノクロ）

`EffectComposer` の最後（`OutputPass` の後）に `ShaderPass` でモノクロ化を1枚挟んでいる。
bloomの輝度判定はその手前でカラーのまま行われるので、光り方には影響しない。
「Post FX」パネルの `monochrome` スライダー（0=カラーのまま、1=完全モノクロ）で調整する。

### 色まわり

- `renderer.toneMapping` は `NoToneMapping`。背景シェーダーは手動で sRGB→linear変換してから
  明るさを掛け、`OutputPass` が最後に linear→sRGB に戻す（二重トーンマッピングを避ける）

## Phase 2（実装済み・実験的、疑似深度）

要件定義書 §5 の「深度マップによるディスプレイスメント＋カメラ移動」を、**本物の深度推定
モデルが無い状態**でまず試すための実験実装。「Depth 3D（Phase 2・実験的）」パネルの
チェックボックスで有効/無効を切り替えられる（無効時はPhase 1と同じ、完全に平面で静止した
見た目に戻る）。

**疑似深度マップ（`generatePseudoDepthGrid()` in `main.js`）。** 本物の単眼深度推定
（Depth Anything V2 等）はこのツール単体では動かせないため、ひとまず画面のY位置を主成分、
輝度を従成分にした簡易的な深度勾配で代用している: 下ほど手前（depth小）・上ほど奥
（depth大、輝度マップのクラスタ割り当てと同じ向き）、明るい画素（ネオン等）はその中で
わずかに手前へ引く。この関数の中身だけを、`batch/` が将来出力する本物の深度マップ
（16bit PNG）や手動アップロードした深度画像の読み取りに差し替えれば、以降のジオメトリ・
カメラ側は無改造で使えるように分離してある。

**ディスプレイスメント。** 背景メッシュ（`PlaneGeometry`）を `computeDepthGridSegments()`
で決めた粗いグリッド（横48分割固定、縦は写真のアスペクト比から算出・最大64分割）に細分化し、
写真読み込み時に1回だけ疑似深度をサンプリングして各頂点のZをその場でずらす
（`reapplyDepthStrength()`）。毎フレームではなく、写真読み込み時と `depth strength`
スライダー操作時のみ再計算するので負荷は小さい。

**カメラ（dolly_in）。** カメラは `OrthographicCamera` から `PerspectiveCamera` に変更。
静止時（振幅0・ディスプレイスメント0）にPhase 1の固定フレームとまったく同じ画角になるよう、
`BASE_CAMERA_Z` からFOVを逆算してある。`tick()` 内で単純な時間ベースのサイン波によりZ位置を
前後させる（要件定義書 §7 の `dolly_in` テンプレート）。MIDI Clock（8小節周期）への位相同期は
未実装で、今は `dolly period` スライダーで指定した秒数の固定周期。

**振幅は小さめが基本。** 要件定義書 §11「深度の破綻はカメラ振幅で隠す」の通り、
`depth strength` / `dolly amplitude` を上げすぎると疑似深度の粗さ（塗りつぶし領域の境界に
できる階段状の折れ目など）が見えやすくなる。デフォルト値は控えめに設定してある。

### その他

- Three.js は `index.html` の importmap で CDN (unpkg) から読み込む。ビルド不要
- `../config/midi-mapping.json` を起動時に `fetch` する。`file://` では動かないため、
  ローカルサーバー経由（`python -m http.server`）か GitHub Pages 経由で開くこと
- 写真・光点データは `<input type="file">` でローカル読み込みし、どこにも送信しない

## Dropbox連携（アプリフォルダからのスライドショー、実験的）

写真を1枚ずつ手動で読み込む代わりに、Dropboxの専用フォルダに入れた写真群を次々と
自動表示できる（「Dropbox」パネル）。

### なぜGoogle Photosではないか

最初はGoogle Photos Picker APIで実装していたが、要望の「アルバム単位で一括指定」を
満たせず断念した。理由は3つ重なっている:

1. Google Photos Library APIの共有アルバム系エンドポイント（share/unshare/get/join/leave/
   list）は2025年3月末で完全に廃止され、以後どんなアプリも（審査済みであっても）
   サードパーティからは呼び出せない（`403 PERMISSION_DENIED`）。「アルバムを公開設定に
   すれば読める」という回避策も存在しない。
2. 代替のPicker API自体にも「アルバムをまるごと選ぶ」ボタンが無く、個別の写真を1枚ずつ
   タップして選ぶ（または検索バーで絞り込んでから複数選択する）操作が必須。
3. 選択セッションも7日で失効し、定期的に選び直しが必要。

Dropboxにはこの種の制約が無い。**「アプリフォルダ」**（`Apps/<アプリ名>/`、Dropbox側が
アプリごとに自動生成する専用フォルダ）にスコープを絞った権限（`files.metadata.read` /
`files.content.read`）だけを要求すれば、それ以外のDropbox全体には一切アクセスできない
状態で、**そのフォルダの中身を1リクエストでまるごと一覧取得できる**。スマホのDropbox
アプリでこのフォルダに写真を移動/コピーしておけば、それがそのままスライドショー対象になる
（要望の「あるディレクトリにまとめたものだけ」をそのまま満たす）。

認証はOAuth 2.0 PKCE（[RFC 7636](https://datatracker.ietf.org/doc/html/rfc7636)）。
サーバーもクライアントシークレットも不要で、ブラウザ単体（Web Crypto APIでの
code_verifier/code_challenge生成）で完結する。`token_access_type=offline` で長期間有効な
`refresh_token` を取得するため、Google Photosのセッションのような期限切れも無く、
一度ログインすれば以降は毎回のアクセストークン更新も自動で行われる
（`ensureDropboxAccessToken()` in `main.js`）。写真本体もブラウザから直接Dropboxへ
リクエストする（どこか別のサーバーを経由しない）。

### Dropboxアプリの作成手順（初回のみ、ユーザー側の作業）

このアプリ用のアプリキーは開発側では発行できない。以下の手順で各自
[Dropbox App Console](https://www.dropbox.com/developers/apps) で作成する。

1. 「Create app」をクリックする。
2. 「Choose an API」は **Scoped access** を選ぶ。
3. 「Choose the type of access you need」は **App folder** を選ぶ（これで
   `Apps/<アプリ名>/` 以外にはアクセスできないアプリになる）。
4. アプリ名を入力し（例: `night-light-vj`）、利用規約に同意して「Create app」。
5. 作成後、「Permissions」タブを開き、**`files.metadata.read`** と **`files.content.read`**
   にチェックを入れて「Submit」する。
6. 「Settings」タブに戻り、以下を設定する:
   - **App key** をコピーしておく（後でランタイムの「Dropbox」パネルに貼り付ける）
   - **OAuth 2 → Redirect URIs** に、実際に開くランタイムのURL（クエリ文字列を含まない、
     例: `https://<owner>.github.io/night-light-vj/runtime/`）を追加する。ローカルで
     `python -m http.server` を使って試す場合は `http://localhost:8000/runtime/` 等も
     追加しておくと便利。**このURLは実際にブラウザで開くURLと完全一致している必要がある**
     （末尾のスラッシュの有無なども含む）。
7. コピーしたApp keyをランタイムの「Dropbox」パネルの「アプリキー」欄に貼り付ける。

### 写真の置き方

1. スマホ等のDropboxアプリを開き、Dropbox上に自動生成された `Apps/<アプリ名で指定した名前>/`
   フォルダを探す（無ければ一度ランタイム側で「Dropboxでログイン」まで済ませると生成される）。
2. VJで使いたい夜景写真だけをそのフォルダに移動/コピーする（サブフォルダに分けても
   まとめて読み込まれる）。対応拡張子は `.jpg` / `.jpeg` / `.png` / `.webp` / `.gif`。

### 使い方・切り替えタイミング

1. アプリキーを貼り付けて「Dropboxでログイン」→ Dropboxの認可画面（このページ自体が
   遷移する）で許可すると、このページに戻ってきて自動的にフォルダが読み込まれる。
2. 2回目以降は、保存された `refresh_token` を使って**クリック無しで自動的に**ログイン状態と
   写真セットが復元される（`tryAutoLoginDropboxOnBoot()`）。
3. フォルダに新しい写真を追加した後は「フォルダを読み込む」を押すと再取得する。
4. 別のDropboxアカウントに切り替えたい等の場合は「ログアウト」を押す
   （`localStorage` の `refresh_token` を削除するだけで、Dropbox側の連携解除は行わない。
   完全に連携を切りたい場合はDropbox側の「接続済みアプリ」設定からも削除すること）。
5. 切り替えタイミングは2通りを両方使える:
   - **一定時間ごとの自動切り替え**（トグル＋秒数スライダー、既定12秒）
   - **MIDIトリガー**: `config/midi-mapping.json` の `role: "scene_cut"`（実測データでは
     SAMPLERトラック）のNote Onで1枚進める。要件定義書 §6 の「SAMPLERトラック＝シーン切り替え
     トリガー」に対応
   - 「◀ 前へ」「次へ ▶」ボタンで手動操作もできる（MIDI/実機が無い環境での確認用）

### 実装上の注意

- 一時的な直接リンク（`files/get_temporary_link` が返す `link`）はCORS対応で認証ヘッダ無しに
  そのままフェッチできる（`files/download` はカスタムヘッダが必須でブラウザから扱いにくいため
  採用しなかった）。有効期限は4時間なので、Google Photos版と同様に全件先読みはせず表示直前に
  都度取得する（`advanceSlideshow()` in `main.js`）
- アクセストークンは短命（数時間）だが、`refresh_token` はclient_secret無しで更新できる
  （PKCEの公開クライアント向け設計）。`ensureDropboxAccessToken()` が期限切れ60秒前を
  目安に自動更新する
- 認可コード（`?code=...`）はページ全体のリダイレクトで受け取り、処理後すぐに
  `history.replaceState()` でURL/履歴から取り除く（ブラウザ履歴にトークン交換用の
  ワンタイムコードを残さないため）
